# Задание исполнителю — прогон 9 (доверенный клиентский IP и лимиты)

Сначала прочитай `PROMPT_COMMON.md`. Ниже только специфика прогона.

## Скоуп

Одна карточка: **VERA-007** — rate limit за прокси становится глобальным (P1).

Карточка одна, но затрагивает четыре слоя: `nginx/`, Next BFF, backend сайта и
Agent Service. Поэтому она вынесена в отдельный прогон и не смешивается ни с
чем другим.

## Суть проблемы

Оба Python-сервиса используют `get_remote_address`. Next.js не передаёт
доверенный клиентский IP в backend сайта, а тот — в HTTP API Agent Service.
Backend видит IP контейнера фронтенда, Agent Service — IP контейнера backend.
Внутренние лимиты в результате общие для всех пользователей: небольшой поток
запросов исчерпывает их для всех.

Одновременно внешний limiter в Next читает первый адрес из `X-Forwarded-For`,
а nginx добавляет `$proxy_add_x_forwarded_for` к тому, что прислал клиент —
то есть первый элемент управляем клиентом и лимит обходится подменой.

## Ключевые решения — реализуй их, не изобретай свои

- **Нормализация только на nginx.** Входящий `X-Forwarded-For` от клиента
  отбрасывается, значение формируется заново из `$remote_addr`.
- **Отдельный внутренний заголовок** для клиентского адреса, который
  проставляет только nginx и который сквозным образом передают Next BFF и
  backend сайта. Не переиспользуй `X-Forwarded-For` для этой цели: он уже
  имеет свою семантику и будет путать.
- **Читать этот заголовок только для запросов из внутренней сети.** Для
  запросов из любого другого источника — падать обратно на `get_remote_address`.
- **Ключ лимита:** для авторизованных `user_id + IP`, для анонимных
  подписанный идентификатор сессии + IP. Голый IP как ключ не оставлять
  нигде.
- **Счётчики остаются в памяти процесса.** Redis-backed limiter нужен только
  при нескольких репликах и относится к VERA-013; сейчас его не вводить.

## Вне скоупа

- Redis-хранилище счётчиков и любые изменения под несколько реплик;
- изменение значений лимитов: правится механизм ключа, а не политика;
- изменение owner-семантики и формата токена анонимной сессии;
- прочие настройки nginx, не относящиеся к нормализации адреса.

## Тесты

- два разных клиента за прокси получают независимые счётчики;
- подменённый клиентом `X-Forwarded-For` не влияет на ключ лимита;
- запрос из внешней сети с внутренним заголовком не получает доверия;
- авторизованный и анонимный ключи различаются;
- прежние значения лимитов и коды `429` с `Retry-After` не изменились.

Проверка на уровне nginx выполняется чтением конфигурации и тестом на
backend/Agent, что заголовок читается по правилам выше.

## Завершение

Сводка по карточке плюс подтверждение: ни один слой не использует голый IP
контейнера как ключ лимита, и подмена заголовка клиентом невозможна.
