# Задание исполнителю — прогон 14 (масштабирование доставки)

Сначала прочитай `PROMPT_COMMON.md`. Ниже только специфика прогона.

## Предусловие

Это самая крупная архитектурная работа из оставшихся. Обязательно должны быть
завершены:

- **прогон 4** — delivery state machine: без точных терминальных исходов и
  аренды параллельная обработка немедленно даст расхождения;
- **прогон 6** — VERA-035: атомарное выделение `sequence_number` является
  прямым предусловием, иначе два обработчика одной сессии получат одинаковый
  номер;
- **прогон 7** — VERA-011 и VERA-012: протокол потока и ограничение ресурсов
  должны быть зафиксированы до смены транспорта событий;
- **прогон 12** — VERA-037: в нём стоит явная проверка «один worker», которую
  этот прогон снимает.

Если что-то из перечисленного не закрыто — остановись и сообщи.

## Скоуп

Одна карточка: **VERA-013** — один worker и `prefetch_count=1` сериализуют
всех пользователей (P1).

Только Agent Service и его инфраструктура запуска.

## Суть проблемы

Agent Service запускается одним worker, consumer имеет `prefetch_count=1`.
Один запрос обрабатывается целиком до следующего, а отправка консультации
может занимать до 360 секунд и всё это время держит единственного consumer.
Добавить worker нельзя: RabbitMQ consumer и SSE-подписчик окажутся в разных
процессах с разными шинами событий в памяти, и ответ не дойдёт.

## Ключевые решения — реализуй их, не изобретай свои

- **События переносятся во внешний stream.** Consumer публикует туда, любой
  web-инстанс читает по `request_id`. Реализация — Redis Streams: Redis уже
  является зависимостью проекта, отдельная инфраструктура не добавляется.
- **Web и worker разделяются на разные процессы.** HTTP и SSE обслуживаются
  web-процессами, очередь — worker-процессами, масштабируются независимо.
- **Работа внутри одной `session_id` сериализуется** распределённой
  блокировкой или партиционированием по ключу сессии. Разные сессии
  обрабатываются параллельно. Это обязательное условие: иначе история
  LangGraph и порядковые номера реплик повредятся.
- **Ограничение «один worker» из VERA-037 снимается**, а его проверка
  заменяется проверкой доступности внешнего stream. Комментарий со ссылкой на
  эту карточку удаляется вместе с проверкой.
- **Повтор событий при переподключении** становится возможен поверх внешнего
  stream с последовательными идентификаторами событий. Схема событий и набор
  их типов, зафиксированные в прогоне 7, не меняются.

## Вне скоупа

- изменение набора типов SSE-событий и контракта ticket;
- изменение delivery state machine, статусов и таблицы исходов;
- изменение payload очереди `agent.requests`;
- переход на другой брокер сообщений вместо RabbitMQ;
- автомасштабирование и оркестрация: задача — сделать несколько экземпляров
  возможными, а не настроить их количество.

## Тесты

Обязательны интеграционные на реальных Redis и PostgreSQL:

- несколько consumer'ов обрабатывают разные сессии параллельно;
- две реплики одной сессии обрабатываются строго последовательно и получают
  разные порядковые номера;
- SSE-подписчик на одном web-инстансе получает события от consumer'а из
  другого процесса;
- переподключение получает пропущенные события из внешнего stream;
- терминальное событие по-прежнему ровно одно на запрос;
- падение одного worker не теряет запрос: аренда истекает и он
  перезахватывается другим.

Нагрузочная проверка: обычный запрос с поиском по базе знаний не блокируется
параллельной долгой отправкой консультации.

## Завершение

Сводка по карточке плюс подтверждение: доставка ответа не зависит от того, в
каком процессе живёт consumer, и один долгий запрос больше не блокирует
остальных пользователей.
