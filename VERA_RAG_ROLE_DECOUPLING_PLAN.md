# Отделение роли пользователя от RAG-поиска Веры

Дата решения: 25 июля 2026 года.

Статус: решение принято; контракт Agent → MCP → RAG переведён на поиск без аудитории. Сам RAG Service и хранящиеся данные не изменяются.

## 1. Цель

Роль пользователя нужна для адаптации финального ответа Веры:

- соискателю или работнику с инвалидностью — акцент на правах, доступных действиях и способах защиты;
- работодателю — акцент на обязанностях, порядке действий и корректной организации условий труда;
- при неизвестной роли — нейтральный ответ, учитывающий обе стороны.

Роль не должна ограничивать источники, участвующие в поиске. Права работника и обязанности работодателя описывают одну правовую ситуацию, поэтому релевантные факты могут находиться в документах с любой старой разметкой аудитории.

Целевой принцип:

```text
роль пользователя → стиль и перспектива финального ответа
текст вопроса     → поиск релевантных фактов по всей базе знаний
```

## 2. Принятое архитектурное решение

Меняются только два сервиса:

1. `vera_agent_service` больше не определяет `seeker`, `employer` или `both` для поиска и вызывает MCP-инструмент только с `query`.
2. `vera_mcp_service` публикует query-only схему инструмента и отправляет в RAG только `query` и `top_k`.

Не меняется `vera_rag_service`:

- `SearchRequest.audience` остаётся опциональным;
- фильтрация по аудитории остаётся доступной для возможных будущих сценариев;
- `audience` остаётся в Postgres, Qdrant payload, ingestion, административном интерфейсе и исторических логах;
- существующие документы не требуют миграции или переиндексации.

Таким образом, мы не удаляем возможность фильтрации из RAG. Текущий продуктовый сценарий Веры просто не передаёт этот фильтр.

## 3. Почему нельзя передавать `both`

В текущем RAG значение `both` не означает «искать по всему корпусу».

Фактическая семантика:

```text
audience="seeker"   → чанки seeker + both
audience="employer" → чанки employer + both
audience="both"     → только чанки both
audience отсутствует → весь актуальный корпус
```

Поэтому правильное решение — полностью исключить поле `audience` из текущего запроса MCP → RAG. Передача значения по умолчанию `both` сохранила бы нежелательный жёсткий фильтр.

## 4. Итоговая цепочка поиска

```text
Agent Service
  TOOL_USAGE_PROMPT:
    - решает, нужен ли поиск;
    - формирует самодостаточный query;
    - не определяет аудиторию для retrieval.
        │
        ▼
  vera_rag_kb(query)
        │
        ▼
MCP Service
  публичная схема: только query
        │
        ▼
  POST /api/v1/search
  {"query": "...", "top_k": 5}
        │
        ▼
RAG Service
  SearchRequest.audience = None
        │
        ▼
  поиск по всему актуальному корпусу
```

`query` должен быть самодостаточным:

- содержать суть вопроса пользователя;
- учитывать существенный контекст из истории диалога;
- не содержать неразрешённых местоимений вроде «он», «у них» или «это»;
- описывать правовую ситуацию, а не желаемый стиль ответа.

## 5. Изменения в Agent Service

Затронуты:

- `app/graph/prompts/system.py`;
- `app/clients/mcp_client.py`;
- unit- и integration-тесты графа, proxy и mock MCP;
- README с публичным контрактом.

Новый контракт локального proxy:

```python
vera_rag_kb(query: str)
```

`TOOL_USAGE_PROMPT` больше не просит LLM угадывать аудиторию. Он требует сформировать самостоятельный поисковый запрос и прямо запрещает ограничивать поиск ролью пользователя.

Описание Веры и её роль по-прежнему остаются отдельными переиспользуемыми частями системного промпта. Указанные в роли две аудитории описывают пользователей ассистента, а не фильтры RAG:

1. Соискатели с инвалидностью и работники с инвалидностью.
2. Работодатели.

## 6. Изменения в MCP Service

Затронуты:

- `app/tools/vera_rag_kb.py`;
- `app/clients/rag_client.py`;
- unit-, contract- и protocol integration-тесты;
- README с контрактами Agent → MCP и MCP → RAG.

Публичная MCP-схема теперь содержит только `query`.

`RagClient.search()` принимает `query` и `top_k`, а HTTP-тело намеренно не содержит `audience`:

```json
{
  "query": "Какие обязанности есть у работодателя при адаптации рабочего места для работника с инвалидностью?",
  "top_k": 5
}
```

Из MCP tracing удалён атрибут `mcp.tool.audience`, потому что аудитория больше не участвует в вызове инструмента.

Из описания MCP-инструмента также удалён статический перечень документов базы. Состав корпуса может меняться и не должен дублироваться в prompt/tool description.

## 7. Что происходит с продовыми данными

Ничего удалять не нужно.

Существующие значения `seeker`, `employer` и `both` продолжают храниться:

- в таблицах Postgres;
- в payload чанков Qdrant;
- в метаданных документов и результатов;
- в исторических поисковых логах.

Когда MCP не передаёт `audience`, RAG не добавляет audience-condition в Qdrant-фильтр. Старые значения не мешают полному поиску и не требуют переразметки.

Если в будущем появится обоснованный сценарий фильтрации корпуса по аудитории, RAG уже технически умеет его поддерживать. Такой сценарий должен быть отдельным продуктовым решением, а не автоматически выводиться из роли пользователя.

## 8. Роль пользователя как следующий этап

Выбор роли в интерфейсе и её передача в Agent Service — отдельная доработка. Она не входит в текущий query-only переход.

Предлагаемая модель:

```python
UserRole = Literal["individual", "employer"]
user_role: UserRole | None
```

Семантика:

- `individual` — соискатель с инвалидностью или работник с инвалидностью;
- `employer` — работодатель;
- `None` — роль не указана, ответ строится нейтрально или по перспективе вопроса.

В интерфейсе значением по умолчанию может быть «Определить автоматически». Это UI-режим, который передаётся агенту как `None`, а не отдельная бизнес-роль.

`user_role` должен использоваться только перед финальной генерацией:

```text
analyze_intent       → без user_role как поискового фильтра
vera_rag_kb          → без user_role
retrieved_chunks     → одинаковы при одинаковом query
generate_*           → формулировка адаптируется по user_role
```

Роль не является признаком авторизации и не должна ограничивать доступ к источникам.

## 9. Порядок деплоя

При раздельном деплое безопасный порядок:

1. Agent Service.
2. MCP Service.

Причина:

- новый Agent отправляет только `query`; старый MCP примет такой вызов и подставит свой прежний default, поэтому контракт временно остаётся совместимым;
- после деплоя нового MCP поле `audience` перестанет попадать в RAG и начнётся поиск по всему корпусу;
- обратный порядок рискован: старый Agent отправит `audience` в новую query-only MCP-схему и может получить ошибку валидации.

Промежуток между деплоями Agent и MCP временно сохраняет старую семантику поиска. Это ожидаемо; функциональное переключение на весь корпус происходит после обновления MCP.

## 10. Проверки и критерии готовности

### Agent Service

- публичная схема локального proxy содержит только `query`;
- tool call в MCP содержит ровно `{"query": ...}`;
- `TOOL_USAGE_PROMPT` не содержит значений `seeker`, `employer`, `both`;
- prompt требует самодостаточный поисковый запрос;
- описание роли продолжает включать обе продуктовые аудитории;
- явный запрет Markdown остаётся частью системного промпта.

### MCP Service

- MCP input schema содержит только `query`;
- `RagClient.search()` не принимает `audience`;
- HTTP-тело RAG-запроса содержит ровно `query` и `top_k`;
- tracing не содержит `mcp.tool.audience`;
- protocol integration-тест подтверждает работу query-only инструмента.

### RAG Service

Код не меняется. Используется уже существующее поведение:

- отсутствие `audience` означает отсутствие audience-фильтра;
- старые чанки всех аудиторий остаются доступными retrieval;
- category, topic, is_actual, dense, sparse, RRF и reranker работают как раньше.

### Сквозной инвариант следующего этапа

```text
same query + different user_role
    → same retrieval request
    → same retrieved chunks
    → role-adapted final wording
```

## 11. Rollback

Изменения не затрагивают схему БД и индекс, поэтому откат не требует миграций.

При необходимости можно откатить версии MCP и Agent. После отката старый MCP снова начнёт передавать `audience` со значением, выбранным старым Agent или равным `both`.

Важно учитывать, что это вернёт старую семантику: `both` ограничивает поиск чанками `both`, а не всем корпусом.

## 12. Итог

RAG отвечает на вопрос: «какие факты и источники релевантны запросу?» — и не знает роль текущего пользователя.

Agent отвечает на вопрос: «как объяснить найденное именно этому пользователю?» — роль будет применяться только на этапе формирования финального текста.

Текущее решение достигает этого без изменений RAG Service и без риска для уже загруженных продовых документов.
