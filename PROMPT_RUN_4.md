## Шаг 2 — Пакет delivery state machine

### Это одно изменение, а не четыре

VERA-004, 014, 015 и 034 описывают один механизм с разных сторон. Реализуются **одним коммитом** — это осознанное исключение из правила «одна карточка = один коммит».

Но **отчёты заполняются во всех четырёх карточках**, каждый со своей стороны механизма и со ссылкой на общий хеш коммита. Не пиши один отчёт и три отсылки «см. VERA-004»: ревью идёт по карточкам.

### Целевой контракт — реализуй его, не изобретай свой

Инварианты, которые должны выполняться после правки:

1. Каждый delivery завершается **ровно одним** `ack` или `nack`.
2. Каждый адресуемый валидный запрос получает **ровно одно** терминальное SSE-событие (`done` или `error`).
3. `done` отправляется **только после** успешного durable commit статуса `completed`.
4. Duplicate replay воспроизводит **сохранённый исход**, а не выводит любой сохранённый ответ как успех.
5. Turn в `processing` с просроченным lease может быть безопасно переобработан.

Таблица исходов:

| Ситуация | Статус в БД | SSE | AMQP |
|---|---|---|---|
| Ответ сформирован, commit прошёл | `completed` | `done` после commit | `ack` |
| Ответ сформирован, commit не удался после ретраев | `delivery_unconfirmed`, ответ сохранён | `error` | `ack` |
| Ошибка до первого токена, ретраи исчерпаны | `generation_failed` | `error` | `nack(requeue=False)` → DLQ |
| Ошибка после первого токена | `stream_interrupted`, частичный ответ сохранён | `error` | `ack` |
| Ошибка после начала мутирующего tool | `delivery_unconfirmed` | `error` с текущим текстом про неподтверждённую отправку | `ack` |
| Пустой stream LLM (VERA-018) | `generation_failed` | `error` | `ack` |
| Дубль: turn с живым lease | не менять | `error` «уже обрабатывается» | `ack` |
| Дубль: turn с просроченным lease | reclaim в `processing` | обработать заново по общим правилам | по итогу обработки |
| Дубль: turn в терминальном статусе | не менять | воспроизвести **сохранённый** terminal event | `ack` |
| Запрос не относится к доступной сессии | не создавать | `error` | `nack(requeue=False)` |
| Невалидный payload (VERA-016) | не создавать | ничего не отправлять | `nack(requeue=False)` → DLQ |

Ключевое отличие от текущего кода: сейчас `delivery_unconfirmed` при повторе воспроизводится как `token` + `done`, то есть ошибка превращается в успех. Должен воспроизводиться `error`.

### Что реализовать

- **Lease.** Использовать существующее поле `ChatTurn.started_at`, добавить `lease_until`, `attempt_count`, `worker_id`. Claim turn атомарно. Живой lease = настоящий дубликат; просроченный = переобработка.
- **Терминальный исход хранить точно.** Заменить обобщённый `failed` на конкретные статусы из таблицы. Сохранять достаточно данных, чтобы duplicate replay воспроизвёл тот же terminal event.
- **Гарантия ack/nack.** Внешний `try/finally` с явной state machine результата: ни один путь не должен оставить delivery неподтверждённым. Отдельно обработать `CancelledError` при shutdown и не скрывать его.
- **Retry persistence.** Transient ошибка сохранения на старте должна получать ограниченный retry, а не уходить сразу в DLQ. Retry сохранения не должен повторять мутирующий граф.
- **Idempotency key.** Перед мутирующим side effect передавать внешнему инструменту ключ на основе `request_id`, чтобы reclaim не отправил письмо повторно.
- **Reconciliation на старте.** При запуске переводить зависшие `processing` с просроченным lease в корректное состояние.

### Миграция

Нужна Alembic-миграция: новые поля lease и новые значения статуса. Именование по образцу репозитория `YYYYMMDD_HHMM_краткое_описание.py`, обязательно рабочий `downgrade`. Существующие строки со статусом `failed` привести к новому значению осознанно, а не потерять.

Проверить на живой БД цикл `upgrade → downgrade → upgrade` и зафиксировать результат в отчётах.

### Тесты

Обязательны на каждую строку таблицы исходов. Дополнительно:

- падение процесса до первого токена, после первого токена и между commit и `done`;
- redelivery turn'а, зависшего в `processing`;
- ошибка БД на start, complete и fail;
- duplicate delivery для каждого терминального статуса;
- graceful shutdown во время работы графа;
- терминальное событие приходит ровно один раз.

Docker запущен, интеграционные тесты обязательны к реальному выполнению. Подменять моками, помечать `skip`/`xfail` или удалять запрещено.

## Шаг 3 — VERA-018

Пустой stream LLM сейчас считается успехом: `anext(stream, None)` возвращает `None`, ответ сохраняется пустым, уходит `done`. Считать это ошибкой контента: повтор допустим только до выдачи первого токена, после исчерпания попыток — `error`, а не `done`. Статус в БД — `generation_failed` согласно таблице выше.

## Шаг 4 — VERA-016

Решение уже принято в карточке и менять его не нужно: невалидный payload по-прежнему уходит в DLQ **без** терминального SSE. Отправлять `error` по произвольной строке `request_id` из невалидного сообщения нельзя — это позволило бы завершить чужой поток.

Деливерабл этого шага небольшой и состоит в фиксации решения: тест, подтверждающий, что при невалидном payload SSE-событие не отправляется и сообщение уходит в DLQ, и комментарий в коде, объясняющий почему именно так. Наружу не должны уходить детали ошибки.

Отдельный коммит, отдельный отчёт.
