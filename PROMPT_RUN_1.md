# Задание исполнителю — прогон 1 (site/frontend)

Ты — исполнитель технических правок в проекте «Работа для всех».

## Рабочая директория

`D:\BKS.Lab\python\my_projects\site_work_for_everyone`

## Главный документ

`VERA_CHAT_TECHNICAL_AUDIT.md` в корне проекта.

## Перед началом работы

1. Прочитай в этом документе раздел **«Инструкция агенту-исполнителю»** целиком. Он имеет приоритет над формулировками внутри карточек и над твоими привычками. Особенно: границы задачи (анти-скоуп), правило остановки, порядок «сначала однорепные карточки».
2. Прочитай карточки, входящие в скоуп этого прогона (список ниже).
3. Прочитай существующий код рядом с местом правки и повтори его стиль: плотность комментариев, именование, идиомы. Новый код не должен отличаться от окружающего.

## Скоуп этого прогона

Строго эти четыре карточки, в этом порядке:

1. **VERA-001** — Authorization в feedback-прокси (P0)
2. **VERA-036** — контролируемая обработка `VERA_SESSION_SIGNING_KEY` (P1)
3. **VERA-002** — единый refresh access-токена для Vera API (P0)
4. **VERA-027** — валидация composer до optimistic append (P1)

Порядок не менять.

VERA-001 и VERA-036 обе требуют вынести формирование owner-заголовков в единый серверный helper — сделай этот helper в VERA-001 и переиспользуй в VERA-036, не дублируй.

## Вне скоупа — не делать ни при каких обстоятельствах

- любые изменения в репозитории `D:\BKS.Lab\python\my_projects\vera_agent_service` (это отдельный git-репозиторий, в этом прогоне он не трогается);
- любые изменения в `backend/` и `nginx/` этого репозитория;
- изменение контрактов: формата SSE-событий, HTTP-схем, payload очереди;
- остальные 34 карточки аудита;
- рефакторинг, переименования и переформатирование кода, не относящегося к правке; удаление существующих комментариев в коде и в `.env`-файлах;
- новые зависимости в `package.json`.

## Известная ловушка в VERA-027

Карточка предлагает при неоднозначном исходе POST делать reconciliation по исходному `request_id`. Это требует серверного endpoint'а и относится к VERA-011/VERA-025, которые в этот прогон не входят.

Поэтому реализуй только frontend-часть: валидация Zod до optimistic append, `maxLength` у textarea, счётчик символов, восстановление черновика при однозначном отказе (`422`/`429`), явный статус доставки сообщения пользователя.

Reconciliation **не** реализовывать — зафиксировать в отчёте как заблокированное VERA-011/025. Это штатное применение «правила остановки», а не недоделка.

## Процесс по каждой карточке

Строго последовательно, одна карточка за раз:

1. Реализуй правку.
2. Добавь или дополни тесты. Использовать существующий раннер `vitest` и существующие файлы, где они есть:
   - `frontend/src/hooks/__tests__/useVeraChat.test.ts`
   - `frontend/src/components/features/vera/__tests__/`
   - `frontend/src/lib/schemas/__tests__/`

   Новый фреймворк не заводить.
3. Прогони проверки из `frontend/`:

   ```
   npm test
   npm run lint
   npm run build
   ```

   Все три должны проходить. Если падает то, что падало до твоей правки, — не чинить, зафиксировать в отчёте.
4. Заполни в `VERA_CHAT_TECHNICAL_AUDIT.md` секцию **«Отчёт исполнителя»** этой карточки (правила ниже).
5. Сделай коммит.
6. Только после этого переходи к следующей карточке.

## Правила заполнения отчёта

- Заполняется секция «Отчёт исполнителя» внутри соответствующей карточки.
- Структуру шаблона не менять: те же пункты, в том же порядке. Заполняй значения после двоеточия, строку `_Заполняется агентом…_` удали.
- **Статус** — одно из: `сделано` | `заблокировано` | `не требуется`.
- **Изменённые файлы** — фактические пути, все до одного.
- **Суть изменения** — 2–4 предложения по существу, без пересказа карточки.
- **Миграции Alembic** — в этом прогоне везде «не требуются».
- **Тесты** — какие файлы добавлены/изменены, точные команды и их результат (например: `npm test` — 42 passed; `npm run build` — ок).
- **Отклонения от предложенного решения и причина** — обязательно, если отступил от предложенного в карточке решения. Если не отступал — «нет».
- **Осталось / связанные карточки** — что осознанно не сделано и почему.

Ничего другого в документе не менять: не трогать текст карточек, другие секции, нумерацию, оглавление и отчёты остальных карточек.

## Коммиты

- Один коммит на карточку. Сообщение на русском языке, в стиле истории репозитория, с указанием ID карточки. Пример:

  ```
  fix(vera): VERA-001 — передача Authorization в feedback-прокси
  ```

- Файлы добавлять командой `git add .` (не перечислять вручную).
- Ветку не менять, в удалённый репозиторий не пушить.

## Если заблокирован

Если карточка требует изменения во втором сервисе, в `backend/` или в `nginx/` — не делай его. Пометь карточку статусом «заблокировано», запиши в отчёт, что именно потребовалось и почему, и переходи к следующей.

## Завершение

Когда все четыре карточки обработаны, выведи короткую сводку: по каждой карточке — статус, число изменённых файлов, результат тестов. Ничего сверх скоупа не предлагай и не делай.
