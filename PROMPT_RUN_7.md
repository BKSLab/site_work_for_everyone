## Скоуп этого прогона

Строго эти четыре карточки, строго в этом порядке:

1. **VERA-011** — SSE-поток защищён ticket-ом (P1, безопасность)
2. **VERA-012** — ограниченные очереди, heartbeat, deadline на сервере (P1)
3. **VERA-024** — раздельные таймауты и обработка heartbeat на клиенте (P1)
4. **VERA-025** — явная state machine доставки на клиенте (P1)

Порядок обязателен и не подлежит изменению: VERA-011 меняет протокол,
VERA-012 добавляет в него события, а VERA-024 и VERA-025 — клиентская сторона
того же протокола. Любой другой порядок означает переписывание клиента дважды.

Одна карточка — один логически завершённый набор изменений и один отчёт. Для
межсервисных карточек допустимы отдельные commits с одним ID карточки в каждом
затронутом репозитории.

## Целевой протокол — реализуй его, не изобретай свой

### Поток запроса

```text
1. Браузер  -> POST /api/vera/chat            (Next BFF -> backend сайта)
2. backend  -> публикация в RabbitMQ
3. backend  -> 202 {request_id, stream_ticket, stream_url}
4. Браузер  -> EventSource(stream_url + "?ticket=" + stream_ticket)
5. Agent    -> проверяет ticket и отдаёт поток событий
```

Сейчас `EventSource` открывается **до** POST, а `202` возвращает
`{"status": "queued"}`. Изменение этого ответа — единственное разрешённое
изменение внешнего контракта в карточке VERA-011.

### Ticket

- **Кто выпускает:** backend сайта, в момент успешной публикации в очередь.
  Он единственный, кто уже проверил владельца сессии.
- **Чем подписывается:** HMAC-SHA256 на ключе, производном от уже существующего
  общего секрета `VERA_AGENT_API_KEY`: `HMAC(api_key, "vera-stream-ticket")`.
  **Новый env-секрет не вводить** — каждое дополнительное ручное равенство
  ключей увеличивает риск, описанный в VERA-037.
- **Полезная нагрузка:** `request_id`, `session_id`, идентификатор владельца
  (`user_id` либо `anonymous_token_hash`), `exp`.
- **TTL:** 60 секунд. Этого достаточно, чтобы браузер открыл поток сразу после
  `202`, и мало для утечки через логи или историю браузера.
- **Одноразовость:** ticket **не** одноразовый. `EventSource` переподключается
  сам, и одноразовый ticket ломал бы штатный reconnect. В пределах TTL ticket
  можно предъявлять повторно для того же `request_id` и того же владельца.
- **Проверка на стороне Agent Service:** подпись, срок, совпадение
  `request_id` из ticket с `request_id` из пути. Несовпадение или просрочка —
  `401`, без деталей в теле ответа.

### Второй подписчик

Сейчас вторая подписка молча вытесняет первую, и первый клиент висит навсегда.

Целевое поведение: **второй одновременный подписчик получает `409` и не
трогает первого**. Освобождение слота происходит при отключении первого
клиента или при терминальном событии.

### События потока

| Тип | Когда | Поля |
|---|---|---|
| `token` | фрагмент ответа | `content` |
| `heartbeat` | периодически, пока запрос обрабатывается | `ts` |
| `done` | ответ сохранён | — |
| `error` | терминальная ошибка | `detail` |

Каждое событие получает возрастающий `id` в пределах `request_id`. Набор
терминальных событий не меняется: их по-прежнему ровно два и ровно одно на
запрос.

**Клиент обязан игнорировать неизвестные типы событий, а не считать их
ошибкой.** Сейчас любой неопознанный тип роняет поток в ветку `error` — из-за
этого heartbeat нельзя было добавить раньше.

### Таймауты

| Где | Что | Значение |
|---|---|---|
| Сервер | интервал heartbeat | 15 секунд |
| Сервер | общий deadline запроса | согласовать с самым долгим инструментом (отправка консультации — 360 с) |
| Клиент | ожидание первого события | 30 секунд |
| Клиент | бездействие (сбрасывается на `token` и `heartbeat`) | 45 секунд |
| Клиент | общий deadline | не меньше серверного |

Сейчас клиент имеет один таймер на 100 секунд, который снимается на первом же
событии и больше не ставится: зависший поток держит интерфейс до nginx timeout
в 3600 секунд.

### Ограничение ресурсов

- Очередь подписчика ограничена сверху. При переполнении медленный клиент
  отключается терминальным `error`; обработка запроса на сервере при этом
  продолжается, и результат остаётся в истории.
- Буферы позднего подключения очищаются фоновой задачей по TTL, а не только
  при следующей публикации.
- Повтор событий при переподключении — только в пределах буфера в памяти.
  **Durable replay в этот прогон не входит**: он требует внешнего event store
  и относится к VERA-013.

## Замечания по конкретным карточкам

### VERA-011 — защита SSE

Затрагивает: Agent Service (`app/streaming/**`, зависимости, настройки),
backend сайта (выпуск ticket, ответ `202`), frontend (порядок вызовов),
`nginx/templates/default.conf.template`.

Отдельно обязательно:

- **ticket не должен попадать в access logs.** Он передаётся в query string,
  потому что `EventSource` не умеет задавать заголовки. Настрой nginx так,
  чтобы значение параметра не логировалось.
- порядок вызовов на клиенте меняется на обратный: сначала POST, потом
  `EventSource`. Буфер позднего подключения на стороне Agent Service остаётся
  и продолжает страховать разрыв между `202` и подключением.
- анонимные и авторизованные сессии работают одинаково; чужой ticket даёт
  `401`, чужая сессия по-прежнему `403`.

Тесты: валидный ticket, просроченный, с чужим `request_id`, с испорченной
подписью, отсутствующий; второй одновременный подписчик; отсутствие ticket в
логах.

### VERA-012 — ресурсы и heartbeat

Затрагивает только Agent Service (`app/streaming/session_bus.py`,
`app/streaming/sse.py`, настройки).

Тесты: heartbeat приходит при долгой обработке; медленный клиент не приводит к
неограниченному росту памяти; просроченный буфер очищается фоновой задачей без
новых публикаций; общий deadline завершает запрос терминальным событием;
терминальное событие по-прежнему ровно одно.

### VERA-024 — таймауты на клиенте

Затрагивает только frontend (`src/hooks/useVeraChat.ts`,
`src/components/features/vera/ChatWindow.tsx`).

Разнеси три таймера по таблице выше. Расширь тип SSE-события heartbeat-ом и
сделай неизвестные типы игнорируемыми. Долгая отправка консультации должна
иметь отдельный пользовательский статус, а не выглядеть как обычное ожидание
первого токена.

Существующие механизмы объявлений для программ экранного доступа обязаны
сохраниться: heartbeat не должен ничего объявлять.

### VERA-025 — state machine клиента

Затрагивает только frontend.

Состояния: `draft → submitting → accepted → processing → streaming →
completed | failed | unknown`.

Ключевое правило: при неоднозначном исходе POST (таймаут, обрыв соединения)
**ответ не удаляется**, а выполняется сверка по исходному `request_id`.

**Отдельный endpoint статуса запроса создавать не нужно.** История диалога уже
возвращает `request_id` и `status` каждой реплики — используй существующий
`GET /api/vera/history/{sessionId}` и найди в нём свой `request_id`. Это
избавляет от расширения HTTP-контракта.

Сообщение пользователя помечается как недоставленное только при однозначном
отказе сервера (`422`, `429`). Новый `request_id` создаётся исключительно
после подтверждения, что первый запрос не принят, иначе появятся два turn и
двойная обработка.

## Вне скоупа — не делать ни при каких обстоятельствах

- VERA-013: внешний event bus, Redis Streams, несколько worker или реплик,
  durable replay и `Last-Event-ID` поверх внешнего store;
- VERA-017: пользовательская отмена запроса;
- VERA-005/029: TTL сессии, закрытие диалога, кнопка «Новый диалог»;
- VERA-010: документация и env-примеры — отдельный финальный прогон;
- переработка delivery state machine VERA-004/014/015/034;
- изменение payload очереди `agent.requests`, owner-семантики и формата
  истории;
- новые env-секреты;
- новые зависимости в `requirements*.txt` и `package.json`;
- рефакторинг и переформатирование несвязанного кода, удаление существующих
  комментариев и `.env`-примеров;
- любые push.
