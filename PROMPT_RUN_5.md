## Скоуп этого прогона

Строго эти карточки, строго в этом порядке:

1. **VERA-030** — cookie создаётся отдельно для каждой session ID (P2)

## Замечания по конкретным карточкам

### VERA-030 — выбери меньший из двух вариантов

Карточка предлагает два решения. **Реализуй второе, меньшее:** оставить per-session cookies, использовать hash полного `session_id` в имени cookie и удалять cookie при истечении сессии.

Первый вариант — единая server-managed cookie анонимного principal с реестром его сессий — **не делай**. Он меняет семантику владения, которую будут перерабатывать VERA-005 и VERA-029, и сейчас создаст работу, подлежащую переделке.

Помни, что карточка сама понижает риск: коллизия имён не даёт доступа к чужой сессии, потому что подписанный payload привязан к полному `session_id` и backend отклонит неверный токен. Это hardening, а не дыра в правах — не раздувай правку.

### VERA-026

Определи Zod-схемы для всех вариантов HTTP-ответов и SSE-событий, безопасно разбирай content type и тело (сейчас `response.json()` падает на пустом или не-JSON ответе), при несоответствии контракту показывай контролируемую ошибку.

**Набор типов SSE-событий менять нельзя** — остаются `token`, `done`, `error`. Добавление heartbeat и обработка неизвестных типов относятся к VERA-012/024 и в этот прогон не входят.

### VERA-028

Буферизуй токены и применяй их к UI пакетами; мемоизируй список сообщений; автоскролл выполняй только если пользователь уже находится около нижнего края, иначе показывай кнопку перехода к новому сообщению.

Осторожно: в `ChatWindow.tsx` уже есть логика сохранения позиции прокрутки при подгрузке старых сообщений (`previousScrollHeightRef`). Её поведение должно сохраниться — при загрузке предыдущих сообщений экран не должен прыгать.

Доступность не должна пострадать: существующий механизм объявлений для программ экранного доступа остаётся рабочим, буферизация не должна приводить к потере последнего фрагмента ответа.
