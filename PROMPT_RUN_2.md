## Замечания по конкретным карточкам

### VERA-036

Отсутствующий или несовпадающий ключ подписи должен давать контролируемый ответ с correlation ID, а не неструктурированный `500`. Создание и чтение owner-токена уже вынесены в `vera-owner-headers.ts` — дорабатывай его, а не пиши второй helper. Проверка обязательного env выполняется на стороне frontend; менять `backend/` для этого нельзя.

### VERA-002

Самая рискованная карточка прогона — она затрагивает авторизацию. Держи в голове:

- refresh должен быть дедуплицирован: несколько параллельных запросов Vera не должны запускать несколько ротаций refresh-токена;
- настоящий ownership `403` повторять автоматически нельзя — его нужно отличать от истёкшего access-токена;
- если для корректного различения понадобится менять коды ответа или контракт backend — это стоп-условие: реализуй только BFF/клиентскую часть, а остальное зафиксируй в отчёте как заблокированное.

### VERA-027

Карточка предлагает при неоднозначном исходе POST делать reconciliation по исходному `request_id`. Это требует серверного endpoint'а и относится к VERA-011/VERA-025, которые в этот прогон не входят.

Реализуй только frontend-часть: валидация Zod до optimistic append, `maxLength` у textarea, счётчик символов, восстановление черновика при однозначном отказе (`422`/`429`), явный статус доставки сообщения пользователя. Reconciliation **не** реализовывать — зафиксировать в отчёте как заблокированное VERA-011/025.

### Уборка (последним шагом, отдельным коммитом)

Это не карточка аудита, отчёт в документе для неё не заполняется. Почини два устаревших теста, которые сейчас падают и шумят в каждом прогоне:

1. `frontend/src/lib/schemas/__tests__/auth.test.ts` — тест подаёт `registerSchema` поле `username`, тогда как схема требует `first_name` и `last_name`. Привести тестовые данные в соответствие со схемой. Саму схему не менять.
2. `frontend/src/components/features/vera/__tests__/VeraFeedbackModal.test.tsx` — ожидается «Спасибо за отзыв!», компонент рендерит «Спасибо за отзыв об Ассистенте Вере!». Привести ожидание в соответствие с компонентом. Сам компонент не менять.

Цель — чтобы `npm test` стал полностью зелёным и в дальнейшем любое падение означало настоящую регрессию.

1. Перед началом карточки заново прочитай раздел **«Инструкция агенту-исполнителю»** в `VERA_CHAT_TECHNICAL_AUDIT.md` и текст самой карточки. Каждый раз, для каждой карточки. Не полагайся на память.
2. Напиши 2–3 строки плана: какие файлы меняешь, что именно, что осознанно не делаешь.
3. Реализуй правку.
4. Добавь или дополни тесты в существующих каталогах (`src/hooks/__tests__/`, `src/components/features/vera/__tests__/`, `src/lib/utils/__tests__/`, `src/lib/schemas/__tests__/`). Новый фреймворк не заводить.
5. Прогони из `frontend/`:

   ```
   npm test
   npm run lint
   npm run build
   ```

   До шага «Уборка» два известных падения (`auth.test.ts > registerSchema > accepts valid data` и `VeraFeedbackModal.test.tsx > allows sending an empty questionnaire with the session id`) считаются существующими: не чинить, но перечислять поимённо в отчёте. После шага «Уборка» падений быть не должно.
6. Заполни секцию **«Отчёт исполнителя»** этой карточки: структуру шаблона не менять, строку `_Заполняется агентом…_` удалить, другие карточки и секции документа не трогать.
7. Коммит: `git add .`, сообщение на русском с ID карточки, без пуша.
8. Переходи к следующей карточке.
