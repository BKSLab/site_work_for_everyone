# Задание исполнителю — прогон 10 (доверие к модели и контекст)

Сначала прочитай `PROMPT_COMMON.md`. Ниже только специфика прогона.

## Скоуп

Строго две карточки, строго в этом порядке:

1. **VERA-021** — tool routing и side effects контролируются преимущественно моделью (P1)
2. **VERA-020** — контекст растёт без trimming и summarization (P1)

Порядок обязателен: VERA-021 определяет, что вообще попадает в контекст из
результатов инструментов, а VERA-020 решает, сколько этого хранить. Обратный
порядок означает выстраивание бюджета вокруг данных, форму которых ещё не
зафиксировали.

Обе карточки — только Agent Service. Frontend и backend сайта не трогать.

## Ключевые решения — реализуй их, не изобретай свои

### VERA-021

- **Параллельные вызовы инструментов запрещены.** Сейчас обрабатывается только
  `tool_calls[0]`, а остальные молча теряются. Если модель вернула больше
  одного вызова — это ошибка маршрутизации, а не повод выбрать первый.
- **Результат MCP разбирается по Pydantic-схеме.** Сейчас берётся первый
  content-блок и `json.loads` без какой-либо проверки формы. Схемы отдельные
  для поиска по базе знаний и для отправки консультации.
- **Мутирующая отправка требует серверно проверяемого условия, а не
  намерения, распознанного моделью.** Минимальное проверяемое условие:
  адрес получателя присутствует в тексте сообщения **пользователя** текущего
  turn, и предыдущий ответ ассистента содержал запрос подтверждения. Оба факта
  проверяются кодом по сохранённой истории, а не промптом.
  Полноценный confirmation token с отдельным хранилищем в этот прогон не
  вводить: он требует новой таблицы и UI-подтверждения, это отдельная работа.
- **Factual и правовые вопросы не могут получить прямой ответ мимо RAG.**
  Запрет на уровне кода, а не инструкции в промпте: если классификация дала
  factual, ветка прямого ответа недоступна — только поиск либо честный отказ.

### VERA-020

- **Явный token budget:** последние N turns целиком плюс безопасная выжимка
  более старых. N и бюджет — настройки, а не константы в коде.
- **Сырой полный результат инструмента не хранится в разговорной истории.**
  Сейчас в `messages` кладётся полный JSON чанков RAG, и он передаётся модели
  на каждом следующем turn. Храни в истории ссылку или идентификаторы, а
  полный результат — отдельно.
- **RAG-контент передаётся как недоверенные данные.** Чёткие разделители и
  инструкция игнорировать команды внутри чанков. Сейчас чанки вставляются
  как `SystemMessage`, то есть в привилегированный контекст — это прямая
  поверхность indirect prompt injection.

## Вне скоупа

- изменение набора SSE-событий и формата истории;
- вывод источников наружу — это VERA-009;
- отдельная таблица и UI подтверждения отправки консультации;
- смена модели, провайдера или параметров генерации;
- изменение контракта MCP-инструментов на стороне `vera_mcp_service`.

## Тесты

Обязательны интеграционные с реальным Redis-checkpointer:

- модель вернула несколько tool calls — маршрутизация отвергает, а не берёт первый;
- искажённый и многоблочный ответ MCP — схема отвергает его предсказуемо;
- отправка консультации без адреса в сообщении пользователя не выполняется;
- отправка после явного подтверждения выполняется;
- factual-вопрос не получает прямой ответ мимо поиска;
- prompt injection внутри RAG-чанка не меняет поведение;
- превышение token budget не роняет запрос и не теряет последний turn.

## Завершение

Сводка по обеим карточкам плюс подтверждение: ни одно решение с внешним
эффектом не принимается только на основании текста, сгенерированного моделью.
