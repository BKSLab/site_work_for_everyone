# Общие правила для всех прогонов правок

Этот файл обязателен к прочтению перед началом любого прогона
`PROMPT_RUN_*.md`. Правила ниже действуют всегда; файл конкретного прогона
добавляет к ним скоуп и технические решения, но не отменяет их.

## Репозитории

- сайт: `D:\BKS.Lab\python\my_projects\site_work_for_everyone`
  (`frontend/`, `backend/`, `nginx/`);
- Agent Service: `D:\BKS.Lab\python\my_projects\vera_agent_service`;
- документ аудита — только в репозитории сайта: `VERA_CHAT_TECHNICAL_AUDIT.md`.

У каждого репозитория своя история Git. Код и тесты коммить туда, где они
лежат. Объединять изменения двух репозиториев в один commit нельзя. Пути с
префиксом `vera_agent_service/...` внутри карточек означают второй
репозиторий, а не подкаталог сайта.

## Перед началом

1. Прочитай раздел **«Инструкция агенту-исполнителю»** в `VERA_CHAT_TECHNICAL_AUDIT.md`.
2. Проверь `git status` обоих репозиториев. Чужие незакоммиченные изменения —
   стоп-условие.
3. Прочитай карточки своего прогона целиком.
4. Прочитай код рядом с местом правки и повтори его стиль: плотность
   комментариев, именование, идиомы. Новый код не должен отличаться от
   окружающего.

## Паттерны кода

Перед любым изменением Python-кода прочитай эталон:

- `site_work_for_everyone\docs\FASTAPI_PATTERNS.md` — для backend сайта;
- `vera_agent_service\FASTAPI_PATTERNS.md` — для Agent Service (файл идентичен).

Слоистая архитектура, трёхслойная система исключений, DI через `Depends`,
стиль докстрингов, структура тестов по слоям. Не заводи второй способ делать
то, что уже делается одним способом.

Для фронтенда — паттерны соседних файлов в `frontend/src/app/api/vera/**`,
`frontend/src/hooks/**`, `frontend/src/components/features/vera/**`.

## Процесс по каждой карточке

1. Перечитай с диска инструкцию и текст карточки. Каждый раз, для каждой
   карточки — не по памяти.
2. Напиши 3–5 строк плана: какие файлы меняешь в каждом репозитории, что
   именно, что осознанно не делаешь.
3. Реализация → тесты карточки → полный набор тестов затронутых репозиториев.
4. Если карточка меняет Agent Service, сначала commit там: его hash нужен для
   отчёта.
5. Непосредственно перед правкой файла аудита перечитай его с диска.
6. Commit в репозитории сайта с ID карточки: код сайта, тесты и отчёт.
7. Следующая карточка без паузы.

## Отчёты

Каждая карточка содержит секцию **«Отчёт исполнителя»**. Заполняется сразу
после реализации, до перехода к следующей карточке.

- структуру шаблона не менять, порядок пунктов сохранять;
- строку `_Заполняется агентом…_` удалить;
- статус — `сделано` | `заблокировано` | `не требуется`;
- «Изменённые файлы» — фактические пути, все;
- «Суть изменения» — 2–4 предложения по существу, без пересказа карточки; для
  Agent Service обязательно указать hash его commit;
- «Тесты» — какие файлы добавлены, точные команды и результат;
- «Отклонения от предложенного решения и причина» — обязательно, если
  отступил; если нет — «нет»;
- «Осталось / связанные карточки» — что осознанно не сделано и почему.

Чужие карточки и остальные секции документа не трогать и не откатывать.

Каталог `backend\tests` не является пакетом: `unittest discover` падает с
`Start directory is not importable`. Запускай файлы напрямую. Pytest в
репозитории сайта не используется, добавлять его нельзя.

Если предыдущие прогоны изменили baseline, возьми фактические числа из их
отчётов и укажи это в своём.

Docker поднят. Интеграционные тесты Agent Service выполняются реально.
Подменять их моками, помечать `skip`/`xfail` или удалять запрещено. Тест
обязан падать, если убрать реализацию.

## Коммиты

Сообщения на русском, в стиле соответствующего репозитория:

```text
# vera_agent_service
[NO-TASK] fix: VERA-0NN — краткое описание

# site_work_for_everyone
fix(vera): VERA-0NN — краткое описание
```

Одна карточка — один commit в каждом затронутом репозитории. Для staging
используй `git add .` и проверь staged diff. **Не пушить ни в одном
репозитории.**

## Общий анти-скоуп

Запрещено без отдельного указания в файле прогона:

- делать что-либо вне описанного в текущей карточке;
- менять публичные контракты: формат SSE-событий, HTTP-схемы, коды ответа,
  payload очереди `agent.requests`, owner-семантику;
- рефакторить, переименовывать и переформатировать несвязанный код;
- удалять существующие комментарии в коде и `.env`-примерах;
- добавлять зависимости в `requirements*.txt` и `package.json`;
- трогать карточки других прогонов;
- пушить.

## Общие стоп-условия

Прекрати работу и спроси пользователя, если:

- потребовалось выйти за границы репозиториев или контрактов, разрешённых
  файлом прогона;
- карточка оказалась шире описанного либо обнаружена смежная проблема —
  зафиксируй в отчёте, но не исправляй;
- падает тест, которого нет в baseline, и причина не доказана сравнением;
- не поднимается окружение для интеграционных тестов;
- принятое в файле прогона техническое решение противоречит коду.

## Номера строк

Номера строк в карточках фиксируют снимок кода на дату аудита. После первой же
применённой правки они недостоверны — навигация по именам файлов, классов и
функций.
