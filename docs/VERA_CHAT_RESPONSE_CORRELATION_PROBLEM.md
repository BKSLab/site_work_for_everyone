# Вера: рассинхронизация и дублирование ответов в чате

Дата фиксации: 22 июля 2026 года. Исправлено: 26 июля 2026 года.

Статус: исправлено в Site и Agent Service.

## Наблюдаемое поведение

При нескольких последовательных сообщениях в одной сессии чат может показывать ответ на предыдущий вопрос вместо ответа на текущий. Следующий запрос получает ответ, ожидавшийся на предыдущем шаге, поэтому диалог начинает отставать на одну реплику.

Дополнительно внутри одного сообщения Веры иногда появляются два близких по смыслу полноценных ответа, склеенных друг с другом.

Пример последовательности:

1. Пользователь спрашивает о документах об инвалидности.
2. Вера отвечает на ранее заданный вопрос о прогуле.
3. Пользователь повторяет вопрос о документах.
4. Вера выдаёт правильный ответ о документах.
5. После нового вопроса об отпуске снова приходит предыдущий ответ о документах.

## Причина рассинхронизации

До исправления `session_id` одновременно использовался:

- как идентификатор истории диалога в Redis/LangGraph;
- как адрес канала доставки SSE;
- как ключ late-connect буфера в Agent Service.

При этом отдельного идентификатора конкретного пользовательского запроса нет.

Frontend открывал `EventSource` по адресу `/vera/sse/{session_id}` и сразу публиковал новое сообщение. `SessionBus` в Agent Service хранил события также только по `session_id`. Если в late-connect буфере оставались события предыдущей обработки, новое SSE-подключение получало их первыми и закрывалось на старом событии `done`. Ответ на только что отправленный вопрос после этого мог остаться без активного подписчика и попасть в буфер до следующего подключения.

Затронутые места:

- `frontend/src/hooks/useVeraChat.ts`;
- `backend/src/schemas/vera.py`;
- `backend/src/services/vera_publisher.py`;
- `vera_agent_service/app/messaging/schemas.py`;
- `vera_agent_service/app/messaging/consumer.py`;
- `vera_agent_service/app/streaming/session_bus.py`;
- `vera_agent_service/app/streaming/sse.py`.

## Причина дублирования

`AgentRequestConsumer._stream_answer()` подписывался на все события LangGraph с типом `on_chat_model_stream` без проверки узла-источника.

В графе есть как минимум два LLM-этапа:

- `analyze_intent` — внутренний анализ и выбор инструмента;
- `generate_direct` или `generate_with_context` — финальный ответ пользователю.

Если используемая модель или адаптер создаёт stream-событие и для внутреннего анализа, consumer отправляет пользователю сначала его содержимое, а затем финальную генерацию. Это объясняет два склеенных ответа внутри одного сообщения.

Consumer теперь явно принимает токены только от финальных узлов по `metadata.langgraph_node`.

## Реализованное решение

Разделить идентификаторы диалога и конкретного запроса:

- `session_id` оставить ключом истории LangGraph;
- для каждого сообщения генерировать новый `request_id`;
- передавать оба идентификатора через frontend, backend, RabbitMQ и Agent Service;
- использовать `request_id` как ключ SSE-подписки и late-connect буфера;
- направлять токены, `done` и `error` только в канал соответствующего `request_id`.

Текущий контракт RabbitMQ:

```json
{
  "session_id": "conversation-uuid",
  "request_id": "message-uuid",
  "user_id": "user@example.com",
  "message": "Какова продолжительность отпуска для инвалидов?"
}
```

Текущий SSE-адрес:

```text
GET /sse/{request_id}
```

В consumer `on_chat_model_stream` фильтруется по `metadata.langgraph_node`; разрешены только:

- `generate_direct`;
- `generate_with_context`.

Контракт строгий: `request_id` обязателен и в Site, и в Agent Service.
Сообщение RabbitMQ без него считается невалидным и отправляется в DLQ.
Fallback на `session_id` для доставки отсутствует.

Изменения MCP, RAG Service, Redis-истории и миграции PostgreSQL не требуются.

## Проверяемые сценарии

Исправление должно сопровождаться следующими сценариями:

1. Два последовательных запроса с одинаковым `session_id` и разными `request_id` получают только собственные ответы.
2. Ответ первого запроса, сохранённый в late-connect буфере, не попадает подписчику второго запроса.
3. Одновременные запросы разных сессий не пересекаются.
4. Одновременные запросы одной сессии с разными `request_id` не пересекаются по SSE.
5. События `on_chat_model_stream` от `analyze_intent` не отправляются пользователю.
6. Токены финального узла приходят один раз и завершаются ровно одним `done`.
7. История диалога продолжает накапливаться по `session_id`, несмотря на новый `request_id` для каждого сообщения.

## Критерии готовности

- каждый вопрос получает только относящийся к нему ответ;
- ответы не отстают на одну реплику;
- внутри одного сообщения нет склеенных дублей;
- позднее подключение SSE по-прежнему получает свой ответ;
- существующая история диалога в Redis не теряется;
- контракт синхронно обновлён во frontend, backend сайта и Agent Service.
