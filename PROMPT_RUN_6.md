## Замечания по конкретным карточкам

### VERA-006 — восстановление Rabbit publisher

Код правится только в `site_work_for_everyone\backend` и в отчёте VERA-006.
`vera_agent_service` для этой карточки не трогать.

После недоступности RabbitMQ или отсутствия provisioned queue во время старта
backend должен восстановить publisher без рестарта процесса. Реализуй один
управляемый механизм восстановления:

- bounded reconnect с ограниченным exponential backoff и корректной отменой
  на shutdown; либо
- ленивую синхронизированную переинициализацию без connection storm при
  параллельных запросах.

Выбор сделай по текущей архитектуре после чтения кода. Нельзя создавать новую
connection на каждый chat request, запускать неограниченные background tasks
или скрывать ошибку бесконечными ретраями.

Обязательно:

- начальная недоступность broker/queue не фиксирует `vera_publisher = None`
  навсегда;
- после восстановления `/api/vera/chat` снова способен вернуть `202`;
- readiness/health отражает фактическое состояние publisher;
- reconnect task/connection корректно закрываются в lifespan;
- существующий Rabbit payload и внешний chat response не меняются.

Покрыть минимум:

- ошибка первого подключения → broker становится доступен → publisher
  восстанавливается без рестарта;
- несколько одновременных запросов не создают несколько reconnect;
- shutdown во время ожидания backoff не оставляет task/connection;
- health/readiness различает unavailable и ready;
- успешная публикация после восстановления возвращает прежний `202`.

**Про живой брокер.** RabbitMQ не поднимается ни одним `docker-compose.yml`
этих проектов — брокер общий и живёт в отдельном проекте `rabbitmq_service_prod`.
У backend сайта нет тестового фреймворка кроме stdlib `unittest` и нет
`testcontainers`, а добавлять зависимости запрещено. Поэтому:

- сама логика восстановления (единственный одновременный reconnect, границы
  backoff, отмена на shutdown, отражение состояния в health) проверяется
  тестами с подставным коннектором — это состояние процесса, а не поведение
  провода;
- живой брокер нужен только для проверки `declare_queue(passive=True)` на
  непровизионированной очереди. Если внешний RabbitMQ доступен — сделай такую
  проверку и опиши её в отчёте. Если недоступен — **это не стоп-условие**:
  зафиксируй в отчёте, что именно осталось непроверенным на живом брокере.

Запрещено обратное: подменить моками так, чтобы тест проходил при неработающем
восстановлении. Тест должен падать, если убрать реализацию.

### VERA-019 — идемпотентный retry графа

Код правится только в `vera_agent_service` и в отчёте VERA-019.

Карточка стала актуальнее после пакета delivery state machine: реплику с
истёкшей арендой теперь можно перезахватить, и граф выполняется на том же
`thread_id` повторно. Каждый прогон создаёт новый `HumanMessage` без
стабильного ID, поэтому история диалога в Redis может накопить дубли вопроса.

Сделай:

- задавать `HumanMessage(id=payload.request_id)` в начальном состоянии графа;
- добавить characterization-тест с **реальным Redis-checkpointer**: повторный
  прогон того же `request_id` не должен дублировать `HumanMessage` в
  восстановленной истории;
- отдельно проверить, что повтор после перезахвата аренды ведёт себя так же.

Не вводить request-scoped namespace checkpoint и не откатывать checkpoint —
эти варианты карточка предлагает только по результатам теста. Сначала тест,
затем минимальная правка. Если тест покажет, что стабильного ID недостаточно,
зафиксируй факт в отчёте и остановись, не переделывая механизм checkpoint.

### VERA-008 — единый контракт отсутствующей history

Это cross-карточка. Разрешённое изменение внешнего контракта строго одно:

- неизвестная в PostgreSQL `session_id` → `404`;
- существующая чужая сессия → `403`;
- существующая доступная сессия → `200` с history.

Основная правка ожидается в Agent Service. Используй существующие domain/service
exceptions и endpoint mapping по `FASTAPI_PATTERNS.md`; не поднимай HTTP-ошибки
из repository/service слоя, если проект использует собственные исключения.

В `site_work_for_everyone` проверь backend proxy/OpenAPI и frontend-ветку
initial `404`. Frontend уже умеет начинать пустой диалог после `404`, поэтому
не делай косметических или дублирующих runtime-изменений. Если regression test
на этот путь отсутствует, добавь его в существующий каталог тестов.

Обязательно проверить на живом PostgreSQL три случая: missing `404`, foreign
`403`, owned `200`. Дополнительно проверить, что backend сайта и Next BFF
сохраняют статус и контролируемое error body, а frontend не показывает
history error для initial `404`.

Не добавляй create/reserve-session endpoint и не реализуй VERA-029. Контракт
`200 + empty` для заранее созданной, но ещё не сохранённой сессии в этот прогон
не входит.

## Процесс по каждой карточке

1. Перед началом карточки заново прочитай с диска раздел
   **«Инструкция агенту-исполнителю»** в
   `VERA_CHAT_TECHNICAL_AUDIT.md` и полный текст самой карточки. Каждый раз,
   для каждой карточки.
2. Перед правкой кода проверь `git status` соответствующего репозитория и не
   затрагивай чужие изменения.
3. Напиши 2–3 строки плана: какие файлы меняешь, что именно и что осознанно не
   делаешь. Для cross-карточки отдельно укажи границу каждого репозитория.
4. Реализация по проектным паттернам → релевантные tests → полный набор tests
   затронутого репозитория.
5. Если код карточки находится в Agent Service, сначала сделай отдельный Agent
   commit: его hash нужен для отчёта в другом репозитории. Для site-only
   VERA-006 этот шаг выполняется после заполнения отчёта, чтобы site-код, tests
   и audit вошли в один commit.
6. Непосредственно перед изменением audit-файла перечитай его с диска.
   Заполняй только отчёт текущей карточки, структуру шаблона не меняй, строку
   `_Заполняется агентом…_` удаляй. Чужие карточки и параллельные изменения не
   трогай и не откатывай.
7. В отчёте перечисли фактические файлы, команды и результаты tests. Для
   Agent Service укажи уже созданный Agent commit hash. Hash site commit,
   содержащего сам отчёт, укажи в финальной сводке — не пытайся вписать hash
   commit в его собственное содержимое.
8. Сделай отдельный site commit с ID карточки: для VERA-006 он содержит
   backend-код, tests и audit; для VERA-019 — только audit; для VERA-008 —
   необходимые site code/tests и audit.
9. Перейди к следующей карточке без паузы.
